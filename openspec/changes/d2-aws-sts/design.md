# Design: D2 AWS STS credentials

## Context
- Shipped: `crates/ls-proxy/src/aws/sts.rs` (synchronous `ureq`, SigV4 via `aws::sigv4`) already implements `assume_role`, `contained` (15 min credentials limited by a session policy) and `revoke_older_sessions`, with tests against a mock HTTP server (`crates/ls-proxy/tests/aws_sts.rs`). `smith aws creds --contained` and `doctor_m7.rs` use it locally. Policy translation lives in `aws/policy.rs`.
- The hosted gateway (`services/gateway`) has agent-token auth, grant cache, binding checks, decrypt, redaction and ledger audit for `/v1/relay`, but no AWS route.
- Agents hold only an agent token (S4). Credentials for AWS are the one allowed exception (H1-2): short-lived, scoped, off by default.

## Goals / Non-Goals
**Goals:** `POST /v1/aws/credentials` in the gateway; `smith aws setup|credential-process|teardown`; a moto service in the local stack; ledger events; console and desktop show AWS bindings.
**Non-Goals:** hosted re-signing relay, per-action policy language, cloud deployment, web-identity federation.

## Decisions and evidence
| # | Decision | Alternatives rejected | Evidence |
|---|---|---|---|
| 1 | **Vend STS credentials from the gateway with `AssumeRole` plus an inline session policy** built from the grant, 900 s default, 3600 s maximum, never the role's full permissions. | Hand out the stored long-lived key (violates H1-2); a hosted SigV4 re-signing proxy (streaming S3 signing and a vendored operation table in the hosted path is a large new surface; the local M7 relay stays for that). | AWS STS AssumeRole docs (docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html): session policies can only narrow the role; 15 minute minimum. In-tree `ls-proxy::aws::sts` proves the call. |
| 2 | **AWS CLI integration through `credential_process`** (`smith aws credential-process` prints the documented JSON `Version/AccessKeyId/SecretAccessKey/SessionToken/Expiration`). | Exporting `AWS_*` env vars (lands in `env`, `ps`, shell history); a wrapper binary around `aws`. | AWS CLI sourcing credentials with an external process (docs.aws.amazon.com/cli/latest/userguide/cli-configure-sourcing-external.html); the CLI caches nothing it must not, and SDKs honour the same setting. |
| 3 | **Gateway holds the base credential or the role's trust**, stored as a sealed secret of kind `aws-assume-role` (role ARN, external id, base key). Agent token only reaches `/v1/aws/credentials`. | Per-agent IAM users (does not scale, long-lived keys); letting the agent call STS itself (needs a base key). | Envelope-encryption spec; AGENTS.md "agents never receive secret values". |
| 4 | **Grant carries allow-lists** (`actions`, `resources`, `max_duration_secs`); the gateway renders them into the session policy and refuses an empty or `*:*` grant unless the binding explicitly says `unrestricted`. | Passing the agent's requested policy through (lets the agent widen scope within the role); a policy DSL now (T2). | STS session-policy rules; M7 `policy.rs` already translates allow rules. |
| 5 | **Tool is off by default**: a binding must set `vend = true` and the grant must carry mode `delegate`; doctor warns that the credentials are agent-visible. | Always on for any AWS binding. | Owner decision H1-2 (`openspec/decisions.md`). |
| 6 | **Test on moto** (`motoserver/moto` in compose) with `AWS_ENDPOINT_URL_STS` pointed at it; the gateway's STS endpoint is configurable for tests only. | LocalStack (licence and account requirements changed in 2025/2026; moto is Apache-2.0 and named in A0-14); the existing hand-rolled mock only. | A0-14 and roadmap row D2; moto STS and IAM support (docs.getmoto.org). Verified by the task 1.2 spike (`tests/e2e/tests/aws_sts_moto.rs`, see "Moto spike findings"): AssumeRole returns usable keys; moto never enforces session policies, even in IAM mode. **Decision:** tests assert the session policy from the request STS received (moto records it per session in `GET /moto-api/data.json`, matched by the returned access key id; a capturing mock where moto is not used), use moto IAM mode only for trust-policy, external-id and signature checks, and leave session-policy enforcement to the P1 real-AWS check. |
| 7 | **Reuse and extend `ls-proxy::aws::sts`** (move the async-callable core to a small `ls-aws` helper only if the gateway cannot call the blocking version through `spawn_blocking`). | Rewriting SigV4 or pulling the full `aws-sdk-sts` (large dependency tree; the in-tree signer is tested against the AWS SigV4 suite). | Existing tests in `crates/ls-proxy/tests/aws_sts.rs` and `tests/fixtures/sigv4`. |

## Moto spike findings (task 1.2, moto 5.1.20)
Test: `cargo nextest run -p ls-e2e --test aws_sts_moto` (skips when moto is unreachable; `E2E_REQUIRE_MOTO=1` makes that a failure). Source checked in the image: `moto/iam/access_control.py`, `moto/sts/{models,responses}.py`, `moto/core/authorization.py`.

| Check | Default mode (IAM off) | IAM mode (`POST /moto-api/reset-auth` body `0`) |
|---|---|---|
| AssumeRole returns `ASIA…` key, secret, session token, `Expiration` = now + `DurationSeconds` | yes; role need not exist, any base key accepted | yes |
| Temporary keys recognised (`GetCallerIdentity` → `assumed-role/<role>/<session>`) | yes | yes, and their SigV4 signature is verified (wrong secret → 403 `SignatureDoesNotMatch`) |
| Base key authenticated | no | yes (unknown key → 403 `InvalidClientTokenId`) |
| Caller needs `sts:AssumeRole` and the role trust policy, incl. `sts:ExternalId` condition | no | yes (wrong external id → 403 `AccessDenied`) |
| Role inline/attached policies limit the session | no | yes (action outside the role policy → 403 `AccessDenied`) |
| **Session policy limits the session** | no | **no**: `AssumedRoleAccessKey.collect_policies` reads only role policies; an action allowed by the role but not the session policy succeeds |
| Session policy validated (JSON shape, 2048 packed-size limit) | no | no (malformed and >2048-char policies accepted; `PackedPolicySize` is a constant) |
| Session policy and external id recorded | yes, `/moto-api/data.json` → `sts.AssumedRole[].policy`, `.external_id` (also holds moto's fake secrets: read only those fields, never print) | same |

Consequences: the renderer (task 2.2) checks shape and the 2048 limit itself; gateway tests (task 3.4) assert the exact policy moto recorded; moto IAM mode is server-global, so moto tests run in the nextest `moto` test group (one at a time) and restore auth-off on exit. Moto quirk: in IAM mode a form parameter containing a space fails signature verification (moto re-encodes the body), though real AWS accepts it; render compact JSON. `MOTO_IAM_LOAD_MANAGED_POLICIES` only preloads AWS managed policies and does not change session-policy handling.

## Binding and grant shape (task 2.1/2.2)
`[[aws_binding]]` in the gateway bindings file (`services/gateway/src/aws_policy.rs`, `AwsBinding`): `secret_id`, `role_arn`, `region`, optional `external_id`, `vend` (default false), `unrestricted` (default false), `max_duration_secs` (default 900). A grant's allow-list is `AwsGrantScope { actions, resources, max_duration_secs }`. `render_session_policy` emits compact JSON: one Allow statement (sorted, de-duplicated actions and resources, nothing else) plus a Deny for credential-minting STS actions. It refuses an empty list (`empty_grant`), `*` actions or resources without `unrestricted` (`grant_too_broad`), malformed entries (`invalid_grant`) and over 2048 characters (`policy_too_large`). `clamp_duration` bounds lifetime by request, grant, binding and the STS 900-3600 s range. Control plane (migration `0014_grant_delegate.sql`): grant mode `delegate` plus a `scope` JSON column (`GrantScope`, same three fields); `POST /v1/agents/{id}/grants` requires a scope for `delegate` and refuses one for `relay`, and `GET /internal/v1/agents/{id}/grants` returns it to the gateway. The gateway `Grant` type reads `scope` in task 3.1.

## How an agent debugs this
`just up` (adds moto on its published port) and `just api`; run `just gateway`; `just aws-vend-smoke` (named `aws-smoke` in the task text; renamed because P1 owns `just aws-smoke`). Ledger: `GET /v1/audit/events` (`aws.credentials.issued`, `aws.credentials.denied`), `just audit-verify`, `just leak-scan`. Inspect moto with `curl $MOTO/moto-api/` and `aws --endpoint-url $MOTO sts get-caller-identity`. Gateway spans in Tempo and logs in Loki through the Grafana MCP; `smith doctor` reports the `aws.vend` check. DB tables: grants and bindings in the control plane (`just psql` or the Postgres MCP).

## Risks
Credentials are visible to the agent for their lifetime (contained by session policy and expiry; stated in the notice and docs). Moto does not enforce session policies (decision 6, spike findings), so enforcement is proven in the P1 smoke check. Clock skew breaks SigV4 (the STS call uses the gateway clock). A hostile upstream echoing credentials is not applicable: the response goes to the caller by design, but the base credential must never appear in it (a test asserts this).

## Gateway route (task 3)
`services/gateway/src/aws.rs`. Request `{secret_id?, role_arn?, duration_secs?}`; unknown fields (an agent `policy`) are ignored. Without `secret_id`/`role_arn` the only AWS binding (or the only one the agent holds a `delegate` grant for) is used. Checks before decrypt, in order: agent token (401), duration below 900 (400 `duration_too_short`), grants read (502), binding (403 `not_bound`, 400 `binding_ambiguous`), `vend` (403 `vend_disabled`), unexpired `delegate` grant (403 `no_grant`), policy render (403 `empty_grant`/`grant_too_broad`/`invalid_grant`/`policy_too_large`), duration clamp. Then decrypt (base credential JSON `{"access_key_id","secret_access_key"[,"session_token"]}`, binding `version`, default 1), `assume_role` on a blocking thread holding the base credential, which also builds the `credential_process` JSON and refuses it (502 `redaction_failed`) if it contains any part of the base credential; the base credential is dropped when that thread returns. STS failures are `sts_error` / `sts_unreachable`, the AWS text is dropped. Response: `{"Version":1,"AccessKeyId","SecretAccessKey","SessionToken","Expiration"}`, `cache-control: no-store`. STS endpoint override `LOCKSMITH_GATEWAY_AWS_STS_ENDPOINT` (moto only).
Ledger: `aws.credentials.issued` (outcome `ok`, retried, credentials withheld with 500 `audit_failed` when it does not land) and `aws.credentials.denied` (the relay outcome codes) once a binding is known. The ledger has no free-form string type, so the role is named by the event's target (the binding's base-credential secret id, which maps to one `role_arn` in the bindings file); `region` is stored as a validated host-label attribute and `duration_secs` as an integer. The control plane's append endpoint accepts these two kinds with `region` and `duration_secs` only.

## Bindings list (task 5.1, D2-1/D2-2)
Source of truth: the gateway bindings file (`[[binding]]`, `[[aws_binding]]`, `services/gateway/src/config.rs`); the control plane and `packages/api-types` did not expose it. This change adds the contract: `BindingView` (`crates/ls-ipc/src/desktop.rs`, generated to `packages/api-types/src/BindingView.ts` by `just api-types`), a union discriminated by `kind` (`http`: `secret_id`, `origin`, `header`; `aws`: `secret_id`, `role_arn`, `region`, `allowed_actions`, `vend`, `max_duration_secs`). It carries no secret, template, external id or credential, and `no_desktop_view_carries_secret_material` covers it. `d3-db-relay` 6.1 adds a `db` variant (name, host, port, user, database, TLS mode). `allowed_actions` come from the `delegate` grants' scopes on the binding (names only), not from the bindings file.
Real vs mocked: real are the type, the fixtures (`@locksmith/api-types/fixtures`), the Bindings page and its sidebar link in `apps/web` (under Agent Gateway) and the Bindings tab in `apps/desktop`, with Vitest tests (rows show role, region, actions, `vend`, max duration; undeclared credential-looking fields are never rendered). Mocked: both apps read the fixtures through a small client interface (`apps/web/src/api/bindings.ts`, `listBindings` in `apps/desktop/src/api.ts`). Not built: the read-only endpoint that reads the bindings file (and joins grant scopes) and serves `BindingView[]`; when it lands, only those two client functions change. It is follow-up work, not part of 5.1.

## 1. The MCP authorization specification (revision 2025-11-25)
Source: https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization

- Applies to HTTP transports ("SHOULD conform"); STDIO servers SHOULD NOT use it and take credentials from the environment. Our existing stdio `locksmith-mcp` is unaffected.
- Roles: the MCP server is an **OAuth 2.1 resource server**; the client is an OAuth client acting for the person; the authorization server may be separate. Locksmith's existing OIDC issuer (T1) can be the authorization server.
- **Protected Resource Metadata (RFC 9728) is mandatory** for the server: the document MUST list `authorization_servers`. Discovery is either a `WWW-Authenticate: Bearer resource_metadata="…"` header on `401`, or a well-known URI (`/.well-known/oauth-protected-resource/<mcp path>` or at the root). Clients MUST support both. Servers SHOULD add a `scope` parameter to the challenge (RFC 6750 §3).
- Authorization server discovery: the AS MUST offer RFC 8414 metadata or OpenID Connect Discovery; clients MUST try both, in the order the spec lists for issuers with and without a path.
- **Client registration**, in the spec's priority order: pre-registered client → **Client ID Metadata Documents** (CIMD, `draft-ietf-oauth-client-id-metadata-document-00`; the `client_id` is an HTTPS URL to a JSON document; the AS advertises `client_id_metadata_document_supported`) → **Dynamic Client Registration** (RFC 7591) as a fallback. Clients and AS "SHOULD" support CIMD; DCR is now a "MAY" fallback.
- Flow: OAuth 2.1 authorization code with **PKCE**.
- **Token audience (RFC 8707 resource indicators):** clients MUST send `resource=<canonical MCP server URI>` in both the authorization and token requests, even if the AS ignores it. The canonical URI is the most specific URI of the server (lowercase scheme and host, no fragment; avoid a trailing slash).
- Token use: `Authorization: Bearer` on **every** HTTP request, never in the query string. The server MUST validate tokens per OAuth 2.1 and MUST check the token was issued **for it as audience**; invalid or expired → `401`, insufficient scope → `403` with `error="insufficient_scope"`.
- **No token passthrough:** servers MUST NOT accept or forward tokens issued for another resource (confused deputy, see the spec's Security Considerations).

## 2. How clients store a remote-MCP token
- **Claude Code** — https://code.claude.com/docs/en/mcp (section "Authenticate with remote MCP servers"): OAuth 2.0 via `/mcp` or `claude mcp login <name>`; "tokens are stored securely and refreshed automatically"; a pre-configured client secret is stored "in your system keychain (macOS) or a credentials file". It supports DCR, CIMD ("discovers these automatically") and pre-configured `--client-id` with a fixed `--callback-port` (`http://localhost:PORT/callback`). It follows a `WWW-Authenticate` header to the AS. Removing a server deletes the local tokens and client registration but does not revoke them at the authorization server; `claude mcp logout <name>` revokes them where the authorization server supports revocation. On `401` with a stored refresh token it refreshes and retries once; without one it reconnects unauthenticated and flags the server for sign-in if that fails.
- **Codex** — source `codex-rs/rmcp-client/src/oauth.rs` and `codex-rs/config/src/types.rs` in https://github.com/openai/codex: OAuth tokens are stored with the `keyring` crate (macOS Keychain, Windows Credential Manager, Linux Secret Service/keyutils) under service "Codex MCP Credentials"; mode `auto` (default) falls back to `CODEX_HOME/.credentials.json` (readable by other processes of the same user); `file` and `keyring` force one store. Codex's MCP client is built on `rmcp`, the crate design.md already picks for the server.
- **Cursor** — **not verified**: its documentation host (`cursor.com/docs`) does not resolve from the VM. Do not rely on any Cursor-specific behaviour; the spec-conformant server below works for any conformant client. Re-check when the host is reachable (task 4.1 end-to-end test uses a scripted client, not Cursor).

Consequence: a token deleted on the client without logout is still valid until it expires, and copies may sit in a plain file. Revocation must be enforced **server-side** on every call, and access tokens should be short-lived.

## 3. Tying a call to an `mcp_clients` row
- The MCP session id (`Mcp-Session-Id`) is chosen per connection and a client can simply `initialize` again, so it is never trusted for authorization (design.md "Client binding for revoke").
- The access token names the OAuth client that obtained it. In the local issuer this is verified in source: Keycloak 26.0.8 sets `azp` ("authorized party", `JsonWebToken.AZP`) on every access token to the client id (`token.issuedFor(client.getClientId())`, https://github.com/keycloak/keycloak/blob/26.0.8/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java, line 1028; claim name in https://github.com/keycloak/keycloak/blob/26.0.8/core/src/main/java/org/keycloak/representations/JsonWebToken.java). JWT access tokens per RFC 9068 carry a `client_id` claim instead (https://datatracker.ietf.org/doc/html/rfc9068, section 2.2; not re-read from the VM). The server reads `client_id` if present, else `azp`, and refuses a token that has neither.
- What the id identifies depends on registration: with DCR each install registers and gets its own id; with a pre-registered client or a CIMD URL the id names the software, so installs of the same software are expected to share one id (inference from how the spec defines these approaches, not stated by it).
- **Hub:** key `mcp_clients` by `(org_id, layer, oauth_client_id, principal_id)` as in design.md. Upsert on `initialize` (display name from `clientInfo`, first and last seen). On **every** request, including `initialize`, look the row up from the token's client id and principal; the revoke check runs **before** the upsert, so a revoked re-`initialize` creates no row. If `revoked_at` is set, refuse with `401` and the `WWW-Authenticate` challenge every token whose sign-in happened before `revoked_at`. `iat` is **not** enough: a refresh after the revoke mints a token with a fresh `iat` (Keycloak `initToken` calls `issuedNow()`). The candidate is `auth_time` (`IDToken.AUTH_TIME` in Keycloak), which a refresh should keep; **unverified** that Keycloak 26.0.8 puts `auth_time` on refreshed access tokens. If it does not, revoke must refuse every token for that client and principal until the person re-approves with consent required (design.md's stricter rule).
- **Granularity:** with a shared client id, revoking covers every install of that software for that person. This is accepted and shown in the Clients page; DCR gives per-install revoke where the issuer allows it.
- **Revoke at the issuer too:** on revoke, also revoke the person's refresh tokens and consent for that client at the issuer (Keycloak admin API, user consent revoke; exact call checked in task 4.2), so the client cannot refresh silently. Require consent for MCP clients so silent browser SSO cannot re-authorise a revoked client without the person approving again.
- **Gateway:** the agent token already names the agent; key the row by `(org_id, layer, agent_id)` and rely on the existing agent revocation (design.md).

## 4. Recommendation for the Hub sign-in (task 4.1)
1. `/mcp` on the control plane is an RFC 9728 protected resource: unauthenticated or invalid requests get `401` with `WWW-Authenticate: Bearer resource_metadata="<base>/.well-known/oauth-protected-resource/mcp", scope="…"`; serve the metadata at that path **and** at the root well-known URI, with `resource` = canonical hub MCP URI and `authorization_servers` = the configured OIDC issuer.
2. Reuse the T1 OIDC issuer as the authorization server (Keycloak locally, the self-hoster's issuer otherwise). No Locksmith-specific token.
3. Registration: support what the issuer offers, in spec order. Ship a documented **pre-registered public client** (PKCE, loopback redirect `http://localhost:<port>/callback`) as the always-works path, which Claude Code accepts via `--client-id --callback-port`; enable DCR (RFC 7591) where the issuer supports it; accept CIMD client ids when the issuer advertises `client_id_metadata_document_supported`.
4. Audience: accept only tokens whose `aud` contains the canonical hub MCP URI; reject tokens minted for the console API and vice versa (no passthrough). Clients send `resource`; if the issuer ignores RFC 8707, configure a dedicated client scope with a fixed audience mapper so tokens still carry the MCP audience.
5. Short access-token lifetime (minutes) with refresh tokens, plus the server-side `mcp_clients` revoke check and issuer-side refresh revoke of section 3.

Those were not checked here; the recommendation works with the fallbacks in points 3 and 4 either way.

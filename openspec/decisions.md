# Decided foundations

Every proposal and design must follow these. To change one, raise a `needs-owner` decision; never contradict a line silently.

**Agents may only append.** Each new line links the `needs-owner` issue where the owner approved it. Never edit or delete existing lines; a reversal is a new line that names the one it replaces. `scripts/check-task-edits.sh` enforces this.

## A0 data and cloud foundations (approved in #37, 2026-11-17; details and evidence in `openspec/changes/archive/2026-11-17-a0-data-and-cloud-foundations/design.md`)
- A0-1 · PostgreSQL 18 everywhere: `postgres:18` locally, RDS or Aurora in AWS, and for self-hosters.
- A0-2 · Vanilla Postgres only; `pgcrypto` only if a spike needs it. No pgmq: jobs use a `FOR UPDATE SKIP LOCKED` table (later `apalis`).
- A0-3 · Aurora DSQL is rejected.
- A0-4 · Multi-tenancy: shared tables, `org_id` on every tenant row, `FORCE ROW LEVEL SECURITY`. The app role is neither table owner nor `BYPASSRLS`; migrations run as a separate owner role. Enterprise may get a dedicated database with the same schema.
- A0-5 · Tenant context is set per transaction with `set_config('app.org_id', $1, true)` in the same sqlx transaction. Session-level `SET` is banned and checked by a lint or test.
- A0-6 · Primary keys are UUIDv7 (`uuidv7()` or app-generated v7). No serial IDs are exposed.
- A0-7 · Every encrypted value carries a versioned header `magic(2) ‖ format_ver(1) ‖ alg_id(1) ‖ key_id(16) ‖ nonce ‖ ciphertext ‖ tag`, with AAD = `org_id ‖ secret_id ‖ version ‖ purpose`. The DEK wrap uses the same header.
- A0-8 · No RDS Proxy at first; each service has its own sqlx pool. Dev uses Aurora Serverless v2 with auto-pause (min 0 ACU). The prod choice between RDS and Aurora Multi-AZ is made in P1 from load numbers.
- A0-9 · Every org row has a `region` from day one. One US region (us-east-1) first, an EU cell later. Regions are separate deployments with no cross-region database. EU data residency is not needed at launch.
- A0-10 · KMS: one customer-managed key per environment per region wraps the gateway keys; a customer-supplied key is an enterprise option. Gateways cache unwrapped DEKs briefly to stay within KMS rate limits.
- A0-11 · Audit hash chain lives in Postgres; signed checkpoints go to S3 Object Lock (compliance mode in prod, governance mode in dev).
- A0-12 · AWS Organizations plus IAM Identity Center. OUs: Security (Log Archive, Audit), Infrastructure, Workloads (`control-plane-{dev,prod}`, `gateway-{dev,prod}`), Sandbox. Control Tower is optional later.
- A0-13 · Compute: ECS Fargate first, Helm kept for self-host. In dev, Fargate tasks (ARM, 0.25 vCPU) exist only during a test session.
- A0-14 · Local parity: every AWS service has a local stand-in that speaks the same protocol, behind a trait or standard interface (Postgres 18, OpenBao transit for KMS, Floci (floci-io/floci) for every AWS API (S3, STS, Cognito...), Keycloak for the OIDC browser flow). Only AWS-only behaviour is tested in dev, each with a named P1 smoke check.
- A0-15 · Users: Cognito user pools (Essentials) in our cloud, Keycloak locally, any OIDC issuer for self-hosters. Services speak generic OIDC only (JWKS-verified JWTs); no Cognito SDK calls on the request path.
- A0-16 · Dev costs under $5/month (about $1–2 idle): an always-on `base` OpenTofu stack and an on-demand `session` stack (`just aws-up` / `just aws-down`, auto-destroyed). Banned in dev: ALB, NAT gateway, VPC interface endpoints, Secrets Manager, Route 53 zones, log retention over 1 day.
- A0-17 · Budget guardrails: a $5/month AWS Budget on the dev account (email at $1 and $3; a deny-create SCP at $5), standing SCPs (one region, no banned items, no large instances, Marketplace, reservations or guardrail changes), and Cost Anomaly Detection.
- A0-18 · No AWS keys in a Claude session. Reads through the AWS MCP server run freely; every mutating call needs owner approval after a change brief (what, cost, blast radius, security, rollback), is tagged `created-by=claude-mcp`, and is imported into OpenTofu or destroyed before the session ends. MCP can never change IAM, Organizations, SCPs, Budgets or Identity Center.
- X1-1 · Platforms for now are macOS and Linux; Windows is not built or tested until Windows parity in GA hardening ([#320](https://github.com/locksmith-hq/locksmith/issues/320)).
- G1-1 · The repository goes public with the agent harness (`.claude/`, `docs/agents/`) visible (option A); the owner runs the flip checklist in `docs/going-public.md` after the g1 PR merges ([#349](https://github.com/locksmith-hq/locksmith/issues/349)).
- H1-1 · Secret values are sealed in the browser before they are sent: HPKE to a per-environment public key whose private half only the gateway may use, with the Rust sealing code compiled to WebAssembly. The API accepts only ciphertext. Details in `docs/design/hub-technical-design.md` section 3.3 ([#363](https://github.com/locksmith-hq/locksmith/issues/363)).
- H1-2 · No MCP tool returns a stored secret value. An agent gets the result of using a key. The only credential an agent may hold is a short-lived, scoped one, issued by a tool that is off by default ([#363](https://github.com/locksmith-hq/locksmith/issues/363)).
- H1-3 · Roadmap order after S6 and X1: human sign-in (T1), the cloud dev environment (P1), the console in three slices on the real API (T3, T7, T8), then members (T6), policy (T2), access requests (T4), notifications (N1), remote MCP (M1), honey tokens (T5) ([#363](https://github.com/locksmith-hq/locksmith/issues/363)).
- H1-4 · Certificates, KMS, Access Broker and Security are later direction, not committed work. No spec for any of them until Agent Gateway and Secret Management are in use in the cloud, and each needs a research note first ([#363](https://github.com/locksmith-hq/locksmith/issues/363)).
- H1-5 · The first cloud milestone is a session-only dev environment within the A0-16 budget; revisit when there is something to demo ([#363](https://github.com/locksmith-hq/locksmith/issues/363)).
- T1-1 · Sign-in UX is option C: our own first screen ("Continue with GitHub / Google / email"; GitHub and Google via the issuer's hint parameter, email via the issuer's themed hosted page; one "Continue" button for a self-hoster's own OIDC issuer). Credentials, MFA and recovery stay with the issuer. First run lands on the hub Overview with an automatic personal org and a dismissible "Get started" checklist; style uses the existing mockup tokens ([#397](https://github.com/locksmith-hq/locksmith/issues/397)).
- M1-1 · Hub MCP client revoke refuses tokens whose `auth_time` is before `revoked_at` and revokes the client's refresh tokens and consent at the issuer; the person may sign in again. If the issuer does not keep `auth_time` on refresh, every token for that client and person is refused until an admin un-revokes ([#493](https://github.com/locksmith-hq/locksmith/issues/493)).
- D2-1 · The console Bindings page (an Agent Gateway page in `apps/web` and `apps/desktop` listing every binding with its kind-specific, non-secret fields) is built by whichever of `d2-aws-sts` 5.1 and `d3-db-relay` 6.1 runs first, on T3's routed shell and shared client; the other adds its kind to that page. T3 does not own it ([#538](https://github.com/locksmith-hq/locksmith/issues/538)).
- T3-1 · The live web console uses the mockup frame (option B): a product-grouped sidebar (Home; Secret Management: Projects, Environments, Secrets; Agent Gateway: Agents, Grants; Activity), the org switcher top right, the user card at the bottom, and pages built from the `packages/ui` kit, styled before the screenshot baselines are locked ([#510](https://github.com/locksmith-hq/locksmith/issues/510)).
- DEP-1 · `glib` 0.18.5 (Dependabot alert 2, unsound `VariantStrIter`, fixed in 0.20) stays in `apps/desktop/src-tauri/Cargo.lock` until GA hardening: it comes only from Tauri 2's GTK 3 stack (`gtk` 0.18.2, Linux only), gtk-rs ships no GTK 3 bindings past 0.18, and Locksmith code never calls `VariantStrIter`; revisit when Tauri moves to GTK 4 ([#552](https://github.com/locksmith-hq/locksmith/issues/552)). - T3-2 · The console learns the caller's org from `GET /v1/orgs/current` (the org bound to the request; a human's org is resolved server-side from the verified user), not from a `/v1/me` endpoint or an org claim in the access token, so no issuer configuration changes. The Shell and Overview show the org name from it once T3 (#489) merges; the amended T3 "First run" scenario is restored then ([#576](https://github.com/locksmith-hq/locksmith/issues/576)). ## Open-core layout (owner decision 2026-11-22; compared against Infisical, PostHog, n8n, Metabase, Mattermost, Langfuse, Sentry, Grafana)
- OC-1 · Paid self-host features are source-available under `ee/` in this repo (`ee/LICENSE`, `LICENSING.md`), reached only through the `ls-entitlements` trait; no open-source crate may depend on `ee/` (`deny.toml`). Unlock, export, read and write are never gated by any plan (AGENTS.md rule, enforced by `CoreOp`). The license text is a draft: counsel reviews it before the first sale. This replaces the "premium code lives only in the private repository" line of `docs/public-private-boundary.md`. The license server, billing, plan catalog and SaaS operations stay private (OC-7).
- OC-2 · Container images, the self-host compose, the Helm chart, signed releases, SBOM and installers are owned by `p2-packaging`; no second change implements them. OpenAPI publication on release and the Dockerfile pin check follow from it (task 5.4, and once Dockerfiles exist).
- OC-3 · Customer-facing AWS Terraform modules, if wanted, go in a separate public repo (the Langfuse and n8n pattern), after `p2-packaging` ships images and the chart. SaaS infrastructure stays in `locksmith-cloud` (owner decision 2026-11-22).
- OC-4 · SDKs, the CLI, plugins and any Terraform provider or Kubernetes operator move to their own repositories only after their APIs stabilize (not before GA hardening), because running changes still span them. Until then they stay in this monorepo.
- OC-5 · Dependabot version-update PRs are not adopted: workers already open `deps:` PRs for advisories. Revisit if the dependency backlog grows.
- OC-6 · The services are not wired to an injected `EntitlementSource` and the free tier has no caps until the first paid feature is specified; that change needs a roadmap row and a research note first, and the owner sets the free-tier limits.

- OC-7 · The license server, billing, the plan catalog and the license-signing key are SaaS-side and private; their decisions are recorded in `locksmith-cloud` (`openspec/decisions.md`, SAAS-1). This repository only defines the contract: the `ls-entitlements` trait and the signed offline license format that `ee/crates/ls-ee-license` verifies.
- OC-8 (owner 2026-11-22) · The backend API (the control plane) moves to NestJS 12 (TypeScript, ESM) built the way Infisical's backend is built (domain modules, data-access stores, plugins and guards), with TypeScript, oxlint, oxfmt and knip run through Turborepo. Rust stays for everything that touches plaintext secrets, keys or proxies: the gateway, `ls-crypto`, `ls-envelope`, KMS access and the audit ledger's signing; the exact boundary is decided in change `b1-nestjs-api` (gates G1 and G2). Migration is a strangler: the Rust control plane serves each endpoint until its NestJS replacement passes the same contract tests. This supersedes the Rust-for-all-services sentence of `openspec/config.yaml` (a protected-file task of that change). Accepted costs: two toolchains, duplicated tenant-isolation tests during the migration, and a rewrite of about 13,000 lines of Rust.
- OC-9 (owner 2026-11-22) · Gates of `b1-nestjs-api`. G1: the Rust core behind the internal API keeps audit append and checkpoint signing, agent and workload token mint and verify, and DEK wrap and unwrap through KMS; authorization decisions live in the NestJS API. G2: the in-flight Rust changes `t6-org-members`, `t7-secret-write` and `t8-sessions-and-revoke` are paused (held by a `needs-owner` issue) and the existing endpoints are ported to NestJS first with the strangler and contract tests; those features are then built in NestJS. Already open PRs for them stay as research and schema input, not as Rust handlers to merge. The hold ends when the owner closes the issue.
- OC-10 (owner 2026-11-22) · Gate G3 of `b1-nestjs-api`: TypeScript is pinned to exactly 7.0.2 for `apps/api` and the shared tsconfig base (with `"types": ["node"]`), on evidence from spike 1.1 (`docs/research/nestjs-typescript7.md`). TypeScript 6.0.3 is the proven fallback; a later task that finds a break may switch to it only with a new line here. NestJS 12 officially documents TypeScript 6, so this is a deliberate step ahead of the framework's guide.
- OC-11 (owner 2026-11-23) · The Rust-for-keys rule (AGENTS.md, OC-8) covers the product: anything that touches customer plaintext secrets, keys or proxies. Crew tooling that holds only the crew's own credentials (GitHub App keys, routine fire tokens), never customer secrets, may be written in Node, because it is glue code where Node is simpler. First user: the AWS tooling dispatcher that replaces GitHub-cron worker dispatch. Conditions: secrets come from a secret store at run time, are never logged, and a test scans logs and outputs for planted fake secrets.

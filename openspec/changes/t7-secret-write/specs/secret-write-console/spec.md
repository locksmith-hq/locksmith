# Spec Delta

## Purpose
A person can add a secret or a new version from the console or desktop; the value is sealed on their device and the API accepts only ciphertext.

## ADDED Requirements

### Requirement: The API accepts only ciphertext
Secret and version creation SHALL accept only a sealed ciphertext, a wrapped DEK and the version number, SHALL return only version metadata, and SHALL NOT accept, return or log a plaintext value, DEK or wrapped DEK.

#### Scenario: Sealed create
- **WHEN** a client posts a validly sealed version for the secret's next version
- **THEN** the response is `201` with the version number and `version_count` increases, and the body contains no value

#### Scenario: Plaintext refused
- **WHEN** a client posts a body with a `value` field
- **THEN** the response is `400` and nothing is stored

#### Scenario: Stale version
- **WHEN** a client posts a version that is not the secret's next version
- **THEN** the response is `409` and nothing is stored

#### Scenario: Cross-org isolation
- **WHEN** org B requests the seal key or posts a version for org A's secret
- **THEN** the response is `404`

#### Scenario: No canary anywhere
- **WHEN** a canary value is written through the sealed route
- **THEN** `just leak-scan` over Postgres, Loki and Tempo finds no encoding of it

### Requirement: Environment seal keys
Each environment SHALL have an active HPKE seal key whose private half is generated by the gateway and stored only wrapped by the KMS, and the control plane SHALL publish its public half with its key id and the secret's next version.

#### Scenario: First request provisions the key
- **WHEN** an environment has no seal key and a member requests it
- **THEN** the response is `503` with a retry hint, and after the gateway provisions it a retry returns the public key

#### Scenario: Retired key still opens old versions
- **WHEN** a key is rotated
- **THEN** versions sealed under the retired key still decrypt at the gateway and new writes use the new key

### Requirement: Sealing happens on the device
The console and desktop SHALL seal the value with the Rust sealing code compiled to WebAssembly before any network call, SHALL keep the value only in the form input until sealed, then clear it, and SHALL NOT persist or log it.

#### Scenario: Request body holds no value
- **WHEN** the browser test submits a canary value through the form
- **THEN** no network request, console message or storage entry contains the canary or its encodings, and the request body holds only ciphertext

#### Scenario: Native and wasm agree
- **WHEN** the committed known-answer vector is sealed natively and in wasm
- **THEN** both outputs open to the same plaintext at the gateway and the vector test passes in both

#### Scenario: Form states
- **WHEN** the key is still being provisioned, the version is stale, or the user lacks access
- **THEN** the form shows a preparing state, a single automatic retry, or a `403` message respectively, and never shows the value again

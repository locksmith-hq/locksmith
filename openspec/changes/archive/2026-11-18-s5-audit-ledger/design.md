# Design: S5 audit ledger

## Context
- S3 (PR 168) writes one `gateway_audit` row per relay. The table has no UPDATE or DELETE grant and RLS by `org_id`, but the database owner can still rewrite it. S4 adds `agent_id` to those rows and introduces agent and grant admin actions.
- `crates/ls-vault/src/audit.rs` already has a tested chain: a length-prefixed canonical encoding under a domain tag, `prev_hash = SHA256(canonical(prev) || mac(prev))`, a verify walk that reports the first broken `seq`, and tail-truncation detection. It is tied to `rusqlite`/SQLCipher and to a local HMAC ratchet keyed by the vault key, which a multi-writer server has no use for.
- `crates/ls-envelope` has the OpenBao transit client and the `BaoToken` type (S2).
- Binding decisions: A0-4 and A0-5 (RLS, per-transaction tenant context), A0-6 (UUIDv7 ids), A0-11 (chain in Postgres, signed checkpoints, S3 Object Lock as the durable anchor), A0-14 (OpenBao as the KMS stand-in).

## Goals / Non-Goals
**Goals:** tamper evidence for every audit event per org, checkable by a command and offline from an export; a ledger that T1, T2 and T4 append to without schema changes (new event kinds only).
**Non-Goals:** prevention of tampering by a database owner (we only detect it), the S3 Object Lock sink, SIEM streaming, a transparency log, retention.

## Decisions and evidence
| # | Decision | Alternatives rejected | Evidence |
|---|---|---|---|
| 1 | **One linear SHA-256 chain per org in Postgres** (`audit_events`: `org_id`, `seq`, `id` UUIDv7, `at`, `kind`, `actor`, `target`, `outcome`, `attrs jsonb` of identifiers only, `prev_hash`, `hash`), primary key `(org_id, seq)`. | A Merkle tree log (Tessera, Trillian); one global chain for all orgs (cross-tenant coupling, and RLS hides other orgs' rows from the verifier) | A0-11; `docs/research/oss-building-blocks.md` row "Audit" (in-house chain, Tessera as the upgrade path); Schneier and Kelsey, "Secure Audit Logs to Support Computer Forensics" (1999), https://www.schneier.com/academic/archives/1999/05/secure_audit_logs_to.html; Crosby and Wallach, "Efficient Data Structures for Tamper-Evident Logging" (USENIX Security 2009), https://www.usenix.org/legacy/event/sec09/tech/full_papers/crosby.pdf (a linear chain needs O(n) to verify; fine at slice scale, and Merkle is the upgrade path) |
| 2 | **Append serialises per org on an `audit_heads` row** (`SELECT ... | 4 | **Signed checkpoints with Ed25519 through OpenBao transit** (`transit/sign/audit-checkpoint`, key type `ed25519`), every 1000 events or 60 s per org that has new events. Verification uses `ed25519-dalek`, which S4 already adds. | HMAC checkpoints (the verifier would need the secret); a signing key on the control plane's disk (an attacker who owns the host could re-sign); ECDSA P-256 (adds a second signature crate) | A0-11; RFC 6962 signed tree heads as prior art, https://www.rfc-editor.org/rfc/rfc6962#section-3.5; OpenBao transit sign API, https://openbao.org/api-docs/secret/transit/#sign-data; AWS KMS Ed25519 support for the P1 swap **[verify]** in P1 |
| 5 | **Gateway appends through an internal control-plane endpoint** (`POST /internal/v1/audit/events`, S3 service token), so there is one chain per org. It writes an `attempt` event before the key unwrap and fails closed (503) if that append fails, then an `outcome` event after the upstream call, retried up to 3 times. A missing `outcome` shows in verify output as an open attempt. **Idempotency:** the `outcome` carries the `attempt` event's id as `attempt_id` (required for `relay.outcome`); the control plane takes the org's head lock, returns the stored event (`200`) when an `outcome` for that `attempt_id` exists with the same fields, `409` when the fields differ, and a partial unique index on `(org_id, attrs->'attempt_id')` for `relay.outcome` backs this up, so a retry after a lost response never appends a second `outcome`. Refusals before the attempt append one `relay.denied` event (one try; the refusal stands either way). | The gateway writing its own chain in its own database (two chains per org, split history); writing only after the call (an upstream call could happen without any audit record) | S3 design decision 2 (the gateway never reads the control-plane database and already calls the control plane for material); `openspec/config.yaml` honest-label rule |
| 6 | **`gateway_audit` becomes read-only legacy:** revoke INSERT; no import, because no production data exists before S5. | Importing old rows into the chain (would sign history that was never chained) | S3 design decision 8 ("S5 moves this into the hash chain") |
| 7 | **The file sink is a directory of JSON Lines per org** (`<org_id>/events-<first_seq>.jsonl`, `<org_id>/checkpoints.jsonl`, and a `cursor.json`), written to a temp file then renamed and fsynced. It sits behind an `AuditSink` trait that the P1 S3 Object Lock sink implements. | Writing straight to S3 now (P1 owns the bucket and its retention; locally it would need moto plus Object Lock emulation); a single growing file (no atomic append) | JSON Lines, https://jsonlines.org/; roadmap S5 ("an export goes to a file sink"); A0-11, A0-16 |
| 8 | **Verify modes:** `--db` (walks each org with a verifier role that has `BYPASSRLS` and SELECT only, used only by the CLI) and `--dir` (an export, offline, public key only). `--db --checkpoints-from <dir>` also loads the trusted checkpoints from the export and fails if any of them is missing from the DB chain or does not match it; `just audit-verify` passes this flag whenever an export exists. Without it, `--db` checks the database only against its own checkpoint rows. Checks: `seq` contiguity, `prev_hash` links, recomputed `hash`, checkpoint signatures, the latest checkpoint's `seq` and hash present in the chain. | A verify inside the API process (it would share credentials with the writer) | A0-4 (the app role never has BYPASSRLS; a separate read-only role is consistent with it) |
| 9 | **Honest label: detection, not prevention.** A database owner can rewrite any event and delete checkpoint rows in the database. Only `--checkpoints-from <dir>` (or `--dir`) detects rewriting of history that an export covers; events newer than the last export remain rewritable until the next export. Re-signing a checkpoint also needs the OpenBao signing token. The file sink is not WORM locally; S3 Object Lock in P1 makes exported checkpoints immutable. | Claiming the ledger is tamper-proof | `openspec/config.yaml` honest-label rule; A0-11 |

Built in-house: the chain and checkpoint logic, because it is small (the vault version is about 600 lines including tests), it defines the audit format, and `oss-building-blocks.md` already records this choice. Searched first: Trillian and Tessera (Go services, and Tessera is the upgrade path), Rekor (too heavy), `pgaudit` (logs statements to the server log and is not tamper-evident), and crates.io for "tamper evident log" and "hash chain" (no maintained crate with Postgres storage and signed checkpoints). All versions are re-checked on crates.io at apply, and S5 adds no third-party crate beyond what the workspace, S3 and S4 already bring.
Licence note: `ls-audit` and the `locksmith-audit` verifier use only permissive crates, so the verifier can ship to customers under Apache-2.0.

## Risks / Trade-offs
- [Append contention on one busy org] → one row lock per org keeps the order simple; measure with `oha` in the smoke test. If p99 append latency exceeds 20 ms at 200 relays/s, batch appends or move to Tessera (a new change).
- [Relay availability now depends on the audit append] → this is deliberate (no unaudited decrypt). The control plane is already on the relay path for material (S3), so no new single point of failure is added.
- [The signing token is on the control plane] → a policy limited to `transit/sign/audit-checkpoint` only; the key cannot be exported; the token is rotated with the stack. In P1, KMS with a key policy replaces it.
- [Clock skew in checkpoint times] → order is by `seq`, never by time; time is informational.
- [Breaking the vault audit format during extraction] → the golden-vector test and the existing `ls-vault` audit tests must pass unchanged before the task closes.

## Migration Plan
New migrations add `audit_heads`, `audit_events` (INSERT and SELECT for the app role, RLS, FORCE RLS), `audit_checkpoints`, `audit_verify_runs`, the `audit_verifier` role, and revoke INSERT on `gateway_audit`. The `gateway_audit` INSERT revoke lands as its own migration with task 3.1 (after `0008`), in the same commit that removes the gateway's `gateway_audit` writer, so no build ever writes to a table it may not insert into. Rollback is a **code revert**, not a config switch: no gated legacy writer is kept, because a writer that cannot INSERT (the revoke) would only fail closed. To roll back, revert the 3.1 commit (the gateway's `PgAudit` writer returns) and add a new forward migration that grants INSERT on `gateway_audit` to `locksmith_app` again (migrations are forward-only; never edit an applied one). The ledger tables can stay, since nothing reads them on the rolled-back path. There is no production data yet.

## How an agent debugs this
- `just up`, then `just audit-smoke` (relay, append, checkpoint, export, verify), `just audit-verify`, `just audit-export`, `just audit-tamper-test`.
- Postgres MCP: `select org_id, seq, kind, outcome, encode(hash,'hex') from audit_events order by at desc limit 20`, `audit_heads`, `audit_checkpoints`, `audit_verify_runs`.
- Grafana/Tempo spans `audit.append`, `audit.checkpoint`, `audit.verify` (attributes: org id, seq, outcome; never field values). Loki: `{service="control-plane"} |= "audit"`.
- OpenBao audit log shows `transit/sign/audit-checkpoint` calls by the control-plane token only.
- `locksmith-audit verify --dir <export> --json` reproduces a failure offline; `just leak-scan` covers the export directory.

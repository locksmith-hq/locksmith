# Design: D2 AWS STS credentials

## Context
- Shipped: `crates/ls-proxy/src/aws/sts.rs` (synchronous `ureq`, SigV4 via `aws::sigv4`) already implements `assume_role`, `contained` (15 min credentials limited by a session policy) and `revoke_older_sessions`, with tests against a mock HTTP server (`crates/ls-proxy/tests/aws_sts.rs`). `smith aws creds --contained` and `doctor_m7.rs` use it locally. Policy translation lives in `aws/policy.rs`.
- The hosted gateway (`services/gateway`) has agent-token auth, grant cache, binding checks, decrypt, redaction and ledger audit for `/v1/relay`, but no AWS route.
- Agents hold only an agent token (S4). Credentials for AWS are the one allowed exception (H1-2): short-lived, scoped, off by default.

## Goals / Non-Goals
**Goals:** `POST /v1/aws/credentials` in the gateway; `smith aws setup|credential-process|teardown`; a Floci service in the local stack; ledger events; console and desktop show AWS bindings.
**Non-Goals:** hosted re-signing relay, per-action policy language, cloud deployment, web-identity federation.

## Decisions and evidence
| # | Decision | Alternatives rejected | Evidence |
|---|---|---|---|
| 1 | **Vend STS credentials from the gateway with `AssumeRole` plus an inline session policy** built from the grant, 900 s default, 3600 s maximum, never the role's full permissions. | Hand out the stored long-lived key (violates H1-2); a hosted SigV4 re-signing proxy (streaming S3 signing and a vendored operation table in the hosted path is a large new surface; the local M7 relay stays for that). | AWS STS AssumeRole docs (docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html): session policies can only narrow the role; 15 minute minimum. In-tree `ls-proxy::aws::sts` proves the call. |
| 2 | **AWS CLI integration through `credential_process`** (`smith aws credential-process` prints the documented JSON `Version/AccessKeyId/SecretAccessKey/SessionToken/Expiration`). | Exporting `AWS_*` env vars (lands in `env`, `ps`, shell history); a wrapper binary around `aws`. | AWS CLI sourcing credentials with an external process (docs.aws.amazon.com/cli/latest/userguide/cli-configure-sourcing-external.html); the CLI caches nothing it must not, and SDKs honour the same setting. |
| 3 | **Gateway holds the base credential or the role's trust**, stored as a sealed secret of kind `aws-assume-role` (role ARN, external id, base key). | 4 | **Grant carries allow-lists** (`actions`, `resources`, `max_duration_secs`); the gateway renders them into the session policy and refuses an empty or `*:*` grant unless the binding explicitly says `unrestricted`. | Passing the agent's requested policy through (lets the agent widen scope within the role); a policy DSL now (T2). | STS session-policy rules; M7 `policy.rs` already translates allow rules. |

Enforcement on real AWS remains the P1 real-AWS check. |
| 7 | **Reuse and extend `ls-proxy::aws::sts`** (move the async-callable core to a small `ls-aws` helper only if the gateway cannot call the blocking version through `spawn_blocking`). | Rewriting SigV4 or pulling the full `aws-sdk-sts` (large dependency tree; the in-tree signer is tested against the AWS SigV4 suite). | Existing tests in `crates/ls-proxy/tests/aws_sts.rs` and `tests/fixtures/sigv4`. |

## Floci spike findings (task 1.2, Floci 2.5.0)
Test: `cargo nextest run -p ls-e2e --test aws_sts_floci`. `assume_role_returns_usable_keys` runs on the compose Floci (skips when it is unreachable); `floci_iam_enforcement` starts its own container with `FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED=true` and `FLOCI_AUTH_VALIDATE_SIGNATURES=true` (startup settings, so the shared compose service is never switched; skips without Docker). `E2E_REQUIRE_FLOCI=1` turns a skip into a failure. Floci's account is `000000000000`; its root key in enforcing mode is `test`/`test`.

| Check | Compose Floci (defaults) | Enforcing Floci (both settings on) |
|---|---|---|
| AssumeRole returns `ASIA…` key, secret, session token, `Expiration` = now + `DurationSeconds` | yes; the role must exist (unknown role → 403 `AccessDenied`), any base key accepted | yes |
| Temporary keys recognised (`GetCallerIdentity` → `assumed-role/<role>/<session>`) | yes; signatures are not checked (a wrong secret still passes) | yes, and their SigV4 signature is verified (wrong secret → 403 `SignatureDoesNotMatch`) |
| Base key authenticated | no | yes (unknown key → 403 `InvalidClientTokenId`) |
| Caller needs the role trust policy, incl. `sts:ExternalId` condition | no | yes (wrong external id → 403 `AccessDenied`) |
| Role inline policies limit the session | no | yes (action outside the role policy → 403 `AccessDenied`) |
| **Session policy limits the session** | no | **yes**: an action the role allows but the session policy does not → 403 `AccessDenied`; the same role without a session policy is allowed |
| Session policy validated (JSON shape, 2048 packed-size limit) | no | no (malformed and >2048-char policies accepted) |
| Session policy readable after the call | none found (no endpoint like moto's `data.json` was found) | none found |

Consequences: the renderer (task 2.2) checks shape and the 2048 limit itself; gateway tests (task 3.4) assert the exact policy from the request a capturing mock STS received and, on Floci, that the issued keys work as the assumed role; enforcement is proven by the spike test on the enforcing container. Unlike moto, Floci accepts a spaced form parameter under signature validation; the renderer still emits compact JSON.

## Binding and grant shape (task 2.1/2.2)
`[[aws_binding]]` in the gateway bindings file (`services/gateway/src/aws_policy.rs`, `AwsBinding`): `secret_id`, `role_arn`, `region`, optional `external_id`, `vend` (default false), `unrestricted` (default false), `max_duration_secs` (default 900). A grant's allow-list is `AwsGrantScope { actions, resources, max_duration_secs }`. `render_session_policy` emits compact JSON: one Allow statement (sorted, de-duplicated actions and resources, nothing else) plus a Deny for credential-minting STS actions. It refuses an empty list (`empty_grant`), `*` actions or resources without `unrestricted` (`grant_too_broad`), malformed entries (`invalid_grant`) and over 2048 characters (`policy_too_large`). `clamp_duration` bounds lifetime by request, grant, binding and the STS 900-3600 s range. Control plane (migration `0015_grant_delegate.sql`): grant mode `delegate` plus a `scope` JSON column (`GrantScope`, same three fields); `POST /v1/agents/{id}/grants` requires a scope for `delegate` and refuses one for `relay`, and `GET /internal/v1/agents/{id}/grants` returns it to the gateway. The gateway `Grant` type reads `scope` in task 3.1.

## How an agent debugs this
`just up` (adds Floci on `localhost:4566`) and `just api`; run `just gateway`; `just aws-vend-smoke` (named `aws-smoke` in the task text; renamed because P1 owns `just aws-smoke`). Ledger: `GET /v1/audit/events` (`aws.credentials.issued`, `aws.credentials.denied`), `just audit-verify`, `just leak-scan`. Inspect Floci with `curl localhost:4566/_floci/health` and `aws --endpoint-url http://localhost:4566 sts get-caller-identity` (any fake key works: the compose Floci does not validate signatures). Gateway spans in Tempo and logs in Loki through the Grafana MCP; `smith doctor` reports the `aws.vend` check. DB tables: grants and bindings in the control plane (`just psql` or the Postgres MCP).

## Risks
Credentials are visible to the agent for their lifetime (contained by session policy and expiry; stated in the notice and docs). The compose Floci does not enforce session policies (decision 6); an enforcing Floci does, and on real AWS enforcement is proven in the P1 smoke check. Clock skew breaks SigV4 (the STS call uses the gateway clock). A hostile upstream echoing credentials is not applicable: the response goes to the caller by design, but the base credential must never appear in it (a test asserts this).

## Gateway route (task 3)
`services/gateway/src/aws.rs`. Request `{secret_id?, role_arn?, duration_secs?}`; unknown fields (an agent `policy`) are ignored. Without `secret_id`/`role_arn` the only AWS binding (or the only one the agent holds a `delegate` grant for) is used. Checks before decrypt, in order: agent token (401), duration below 900 (400 `duration_too_short`), grants read (502), binding (403 `not_bound`, 400 `binding_ambiguous`), `vend` (403 `vend_disabled`), unexpired `delegate` grant (403 `no_grant`), policy render (403 `empty_grant`/`grant_too_broad`/`invalid_grant`/`policy_too_large`), duration clamp. Then decrypt (base credential JSON `{"access_key_id","secret_access_key"[,"session_token"]}`, binding `version`, default 1), `assume_role` on a blocking thread holding the base credential, which also builds the `credential_process` JSON and refuses it (502 `redaction_failed`) if it contains any part of the base credential; the base credential is dropped when that thread returns. STS failures are `sts_error` / `sts_unreachable`, the AWS text is dropped. Response: `{"Version":1,"AccessKeyId","SecretAccessKey","SessionToken","Expiration"}`, `cache-control: no-store`. STS endpoint override `LOCKSMITH_GATEWAY_AWS_STS_ENDPOINT` (Floci or a test stub only).
Ledger: `aws.credentials.issued` (outcome `ok`, retried, credentials withheld with 500 `audit_failed` when it does not land) and `aws.credentials.denied` (the relay outcome codes) once a binding is known. The ledger has no free-form string type, so the role is named by the event's target (the binding's base-credential secret id, which maps to one `role_arn` in the bindings file); `region` is stored as a validated host-label attribute and `duration_secs` as an integer. The control plane's append endpoint accepts these two kinds with `region` and `duration_secs` only.

## Bindings list (task 5.1, D2-1/D2-2, D3-1)
Source of truth: the gateway bindings file (`[[binding]]`, `[[git_binding]]`, `[[pg]]`, `[[aws_binding]]`, `services/gateway/src/config.rs`). Per D3-1 the page and its contract come from `d3-db-relay`: the gateway publishes a non-secret inventory at startup (`PUT /internal/v1/gateway/bindings`, `services/gateway/src/bindings_publish.rs`) and the control plane serves it on `GET /v1/bindings` (`BindingSummary`, `services/control-plane/src/api/bindings.rs`, `packages/control-plane-client`). That contract already names the AWS fields (`role`, `region`, `vend`, `max_duration_secs`; no external id, secret id or key). This change adds the AWS kind to the gateway's published inventory and tests that the web and desktop pages render AWS rows without credential fields. The earlier fixture-only `BindingView` contract in `crates/ls-ipc` and `packages/api-types` was dropped when main's contract landed (merge of 2026-11-23). `allowed_actions` is not shown: it belongs to each `delegate` grant's scope, not to the binding, and the D3 contract has no field for it.

## Decision 8: allowed actions on the bindings page (task 5.1)
| # | Decision | Alternatives rejected | Evidence |
|---|---|---|---|
| 8 | **`GET /v1/bindings` serves an AWS-only `allowed_actions`**: the sorted, de-duplicated IAM action names of the org's unexpired `delegate` grants on that binding's base-credential secret, computed by the control plane on each read in the same `with_org` (RLS) transaction as the snapshot. Names only: no resources (ARNs can name buckets, accounts and paths), no `max_duration_secs` per grant, no policy body, no agent names. An AWS row with no such grant shows `[]` ("none"); an AWS row published without a secret id (an older gateway) and every other kind carry no field. To join a row to its grants, the gateway now publishes the AWS row's `secret_id` (an id, never a value; the control plane already holds every secret id and the grants API already shows them). The control plane stores it inside the snapshot (`PublishedBinding`, `PUT` schema only), refuses it on any other kind and never serves it (`BindingSummary` has no such field). The gateway cannot publish `allowed_actions` (unknown field, 400). This supersedes the last sentence of "Bindings list" above ("`allowed_actions` is not shown"). | Leave the actions off the page (task text asks for them); a separate grants view per agent (the page could not tie a grant to a binding without the same join key); join by role ARN (the control plane cannot read the role, it is inside the sealed `aws-assume-role` secret); a hashed join key (the control plane can hash every secret id, so it hides nothing); a new column or migration (the `items` jsonb already holds the id); `#[serde(flatten)]` to share fields between the two types (serde ignores `deny_unknown_fields` on a flattened struct, so the `PUT` would accept unknown fields). | `services/control-plane/src/api/bindings.rs`; tests `bindings_aws_rows_show_allowed_actions_of_the_orgs_delegate_grants_only` (another org's grant on a secret id named in this org's snapshot never shows; relay and expired grants, resources and the secret id never appear) and `bindings_publish_summaries_carry_non_secret_fields_only` (only the AWS row carries `secret_id`); web and desktop Vitest render the actions and never a credential-shaped field injected into the payload. **Owner note:** this narrows the D3 snapshot invariant "no secret id" (d3-db-relay design decision 10, the `bindings.rs` and `bindings_publish.rs` module docs, the migration 0014 comment, which is left as is because the migration is applied) to "no secret id served; AWS rows publish one as a join key". |
